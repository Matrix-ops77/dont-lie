# YubiKey 5.7+ Ed25519 signing backend

**Status:** design only · **Tier 3** (ship 6–12 weeks after a customer asks) · **Date:** 2026-07-29
**Closes:** `tech_edge_2026.md` §3; SYNTHESIS_2026 §7 #8.

---

## 1. Why YubiKey

v1 stores the Ed25519 signing key in the OS keychain (or a `0600`
file fallback). That defends against **file exfiltration**. It does
**not** defend against a malware-tainted userland process that
calls `sign_bytes(payload)`. A YubiKey closes that gap: the key
**never leaves the chip**, every signing op is gated by a physical
touch, and a PIN policy enforces operator presence. For the
regulated buyer (HIPAA §164.312(a)(2)(iv), SOC 2 CC6.1, EU AI Act
Art. 9) the framing is "**cryptographic identity rooted in
hardware**." The YubiKey 5 series is FIPS 140-3 Level 3 validated —
the strongest single-sentence control narrative Don't-Lie can offer.

## 3. Why not Secure Enclave

SE does not support Ed25519. Migrating to P-256 ECDSA would break
every existing receipt, every verify call, every portable bundle,
and every SCITT export. **Honest path:** YubiKey for Ed25519 now;
Secure Enclave as a v3.5 separate product that introduces a
parallel receipt type `signature_alg: "ecdsa-p256-se"`. The v1
receipt format stays unchanged.

## 4. Integration — the `SigningBackend` protocol

`dontlie/sign.py` calls `Ed25519PrivateKey.sign(payload)` on a
`KeyPair` loaded from disk. Make it a protocol with three backends:

```python
class SigningBackend(Protocol):
    def public_key(self) -> Ed25519PublicKey: ...
    def key_id(self) -> str: ...
    def sign(self, payload: bytes) -> bytes: ...
```

- `KeychainBackend` — wraps today's `KeyPair`. Default.
- `YubiKeyBackend` — PKCS#11 client to a YubiKey 5.7+ in PIV slot `9c`.
- `TpmBackend` — v3.5+ work item.

Factory: `signing_backend()` reads `DONTLIE_SIGNING_BACKEND`
(`keychain` | `yubikey` | `tpm`).

### CLI

```bash
dontlie keygen --yubikey --slot 9c --pin-policy once --touch-policy cached
dontlie sign --yubikey                # auto-detect inserted YubiKey
dontlie anchor daily --yubikey        # daily Merkle root on hardware
```

`--touch-policy cached` keeps the touch valid 15 s so batch signing
(Merkle root, witness attestations) does not require one touch per
signature.

### Reference PKCS#11 invocation

```python
import pkcs11
from pkcs11 import KeyType, Mechanism

lib = pkcs11.lib("/usr/lib/yubikey-piv-tool.so")
token = lib.get_token(token_label="dontlie")

with token.open() as session:
    session.login(pin)                          # PIN cached 15s
    priv = session.get_key(key_type=KeyType.EC_EDWARDS,
                           label="dontlie-yk", private=True)
    sig = priv.sign(payload,
                    mechanism=Mechanism.ECDSA_SHA256)  # 64-byte Ed25519
    return priv.public_key, sig
```

Slot `9c` is generated by `yubico-piv-tool -a generate -s 9c -A ED25519`.
The CLI prompts before overwriting an occupied slot.

## 5. "No key fallback" threat model

**The YubiKey is the only copy of the private key.** Lose it,
break it, or fail the PIN (3 wrong tries → PIV applet reset) and
you cannot sign **new** receipts. Old receipts remain valid — the
**public key is on disk** and in every bundle, so the verifier
checks them offline forever.

**This is the same threat model as the current OS keychain.**
`sign.py` is already explicit: `~/.config/dontlie/keys/dontlie.key`
is the single copy. Delete it without a backup and you cannot
sign new receipts. YubiKey does not introduce a new risk; it
strengthens an existing one.

**Mitigations** (already implied by v1 docs): public key on disk →
past receipts verify forever; CLI recommends an offline backup at
keygen; a second YubiKey registered to the same identity is a
documented recovery path; receipts carry `key_id` so an auditor
can identify which key signed which receipt after loss.

This is not key escrow. The YubiKey is not an HSM service. The
operator holds the key.

## 7. Migration from v1

One-line config change. Receipt format unchanged. Verify path
unchanged (public keys are interchangeable between YubiKey and
software keychain — both 32-byte Ed25519, exported as SPKI PEM).

```bash
dontlie keygen --yubikey --slot 9c
export DONTLIE_SIGNING_BACKEND=yubikey
```

**Effort estimate:** ~150 lines of Python (`YubiKeyBackend` class,
PKCS#11 detection helper, `--yubikey` flag plumbing, tests). The
only v1 file that changes structurally is `sign.py`.
